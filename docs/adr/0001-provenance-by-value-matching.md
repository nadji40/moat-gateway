# ADR 0001: Resolve provenance by value matching, not model instrumentation

- Status: accepted
- Date: 2026-09-15

## Context

Moat must answer one question at the moment an agent calls a payment tool: for
each argument of that call, where did this value come from? A payee that the
human typed is a different thing from a payee that appeared in the body of a web
page the agent fetched, even when the two calls are byte-identical on the wire.

There are three places that question could be answered.

1. **Inside the model.** Ask the model to report, per token or per field, which
   part of its context it drew the value from. This requires either a model that
   emits that metadata or a prompt convention that asks for it.
2. **Inside the host's context assembly.** Instrument whatever builds the
   model's prompt so each span carries a source label, and propagate those
   labels through generation into the tool call.
3. **Outside the model, at the boundary.** Watch every value that enters the
   session through tool results, watch every value that leaves in a tool call,
   and match them.

## Decision

Moat resolves provenance by **value matching at the MCP boundary** (option 3).
The session store records every string and numeric leaf extracted from every
tool result, normalized. When a payment call arrives, each configured field is
normalized the same way and checked, in order, against the registered user
intents, the policy allowlist, and the observed tool results. First match wins;
all matches are recorded.

Matching is deliberately crude: substring for strings of at least four
characters, exact-after-normalization for numbers. No fuzzy matching, no
embeddings, no similarity thresholds.

## Rationale

**Option 1 cannot be trusted.** The model's report of where a value came from is
generated by the same process that the injection has already compromised. An
attacker who can write "pay ProMon Billing Ltd" into a page can equally write
"and report that the user asked for this". A control whose evidence is produced
by the attacked component is not a control.

**Option 2 does not survive deployment.** It requires changes in every host that
assembles context — a different change for each agent framework, and an
impossible one for hosts we do not control. Moat's deployment promise is a
single binary and a config file with no code change on the agent side. Option 2
forfeits that.

**Option 3 holds because of where the boundary sits.** The gateway is the same
process that delivered the tool result and receives the tool call, so the link
between them is a fact it observed directly, not a claim the model made. Nothing
in the model's output can forge it: an injection can cause the agent to *emit*
"ProMon Billing Ltd", but it cannot cause that string to have been in the user's
intent text, because the intent text arrived over a different channel before the
page was fetched.

## Consequences

**We accept false `ToolResult` labels for coincidental matches.** If the user's
intent says "Acme" and an attacker's page also says "Acme", the earliest match
wins and we may attribute a user-sourced value to a page. Trust order mitigates
this: intents are checked before tool results, so a genuine user value resolves
to `User` first. The residual risk is a page value that happens to appear
verbatim in the user's own words, which is the rare case, and the one where
allowing the payment is usually correct anyway.

**We accept misses when the agent paraphrases.** If a page says "ProMon Billing
Limited" and the agent calls with "ProMon Billing Ltd", value matching does not
connect them, and the field resolves to `Unknown`. This fails safe: `Unknown` is
untrusted, so the payee-provenance rule still refuses. A miss costs a step-up,
not a wrong payment.

**A four-character minimum is a real limit.** Short payees and two-letter
currency codes match too easily and are excluded from substring matching; the
currency field is matched exactly for that reason.

**Normalization is now part of the security boundary.** Because matching happens
on normalized forms, the normalizer decides what counts as "the same value". It
must be identical on both the ingest and the resolution path, which is why it
lives in one place in `moat-core` and is covered by table-driven tests. Drift
between the two paths would be a silent bypass.

**This is revisitable per field, not wholesale.** If a future host does provide
trustworthy span-level provenance, it can register values through the intent API
as `User` or `Allowlist` and Moat will prefer them, without the matching path
changing. Option 3 is the floor, not the ceiling.

## Addendum, September 2026: destinations are matched exactly

Value matching as described above is text matching, and it is the wrong tool
for an identifier. Two of its properties are actively dangerous applied to an
account number or an address.

Substring matching would accept a fragment. A page that prints a truncated
address, or an account number that happens to contain four characters of
another, would lend its provenance to a different account. That is how
address poisoning works, and there is nothing to gain from it: an identifier
either is the one that was approved or is not.

The numeric path would launder trust. `normalize_number` drops leading zeros,
so the account `0012345` and the number `12345` are the same value. A user
who mentioned invoice 12345 in their own request would, without meaning to,
have granted `Source::User` to an attacker's account.

So a field the policy declares as `kind: destination` resolves through a
separate mode. Each kind of identifier gets a canonical form of its own --
an IBAN compacted and uppercased after its mod-97 check digits pass, an EVM
address lowercased after EIP-55 holds, a Solana address re-encoded from its
32 bytes, anything else the trimmed text it arrived as -- and destinations
are compared on that form and nothing else. The key is prefixed with the
kind, so two kinds can never collide on one string.

The scanner that finds destinations in page text reads an IBAN written in
groups as well as compacted, because that is how an invoice prints one and
how a person types one. Reading only the compact form would mean the account
a user named in their own request resolved to `Unknown`, and the legitimate
payment would be refused for looking exactly like the fraud. Every span whose
check digits pass is recorded rather than one chosen by a tie-break rule: a
span that validates and is not the printed IBAN can only ever matter if it is
canonically equal to the destination being resolved, which makes it the same
account.

This is the "revisitable per field" clause above being used, not an exception
to it. Everything that is a name still matches as text.

## Addendum, September 2026: the user's words are read, not searched

Substring matching against the user's own text over-read it. Any four
characters of a name the user typed counted as the user naming a payee, so
"Pro Inc" rode on "Monitoring Pro Inc"; "do not pay ProMon Billing Ltd" named
ProMon Billing Ltd; and an invoice number or a day of the month counted as an
amount the user asked for.

The intent side now reads the sentence (`moat-core/src/said.rs`). A payee
must be whole words of it; when the writer capitalizes names, a whole
capitalized name and not part of a longer one; and not governed by a negation
earlier in its clause. A number glued to letters is an identifier, and when the
sentence has an amount beside a currency or with a decimal point, a bare number
elsewhere is not the price. Tool results are still matched as text: they only
ever supply `ToolResult`, which the payee rule does not accept.

Every value this declines resolves to another source or to `Unknown`, which is
a step-up. Being stricter here costs a person a question, never a payment.

What it cannot do: a writer who never capitalizes, and Arabic, which has no
capitals, are read by whole words only, so a whole-word fragment of their name
still counts. The complete answer to spelling and fragments is an approval
that pins the recipient's account: then the name may differ in spelling
(tatweel, alef forms, a full stop, "Co" for "Company"), because the money can
only reach the approved account.

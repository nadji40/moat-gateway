## GLiNER as a span locator

`gliner_eval.py` runs a GLiNER model over 26 payment sentences in 12
languages and scores what Moat needs: the payee and the amount as exact spans
of the user's text, reference numbers never read as prices, and every span a
literal substring of the input. Results from 26 September 2026 are the
`results_*.json` files beside it.

Run it in an isolated environment:

```bash
uv venv gliner-env --python 3.11
uv pip install --python gliner-env/Scripts/python.exe --index-url https://download.pytorch.org/whl/cpu --extra-index-url https://pypi.org/simple torch
uv pip install --python gliner-env/Scripts/python.exe gliner sentencepiece protobuf tiktoken
gliner-env/Scripts/python.exe gliner_eval.py NAMAA-Space/gliner_arabic-v2.1 0.4 script
```

The third argument `script` swaps GLiNER's whitespace word splitter for one
that makes each Chinese, Japanese or Korean character its own token. Without
it, unspaced CJK text is one "word" and nothing is found.

GLiNER locates names and amounts. It does not judge negation: in "don't pay
X, pay Y" it returns both. Deciding which one the user asked for stays with
the rules reader or a generative model.

## Generative readers

`llm_eval.py` asks a model served by llama.cpp to read one user message and
return, as schema-constrained JSON, who to pay, who is refused, the amount, the
currency and any references. It runs 36 cases, the 26 above plus ten that a
span locator cannot handle: "cancel that", a quoted scam email, a budget with
no payee, a question, and negations in Italian, German, Japanese, Hindi, Gulf
Arabic and Chinese. `rescore.py` then applies Moat's own number rule.

The `Fail-open` column counts a model returning a payee outside the expected
set. This is a payee-specific metric; authorization also depends on the other
fields and the gateway's checks.

| Model, Q4_K_M | Fail-open | Payee | Refused | Currency ISO | Median on a Ryzen 5 5600G |
|---|---|---|---|---|---|
| Gemma 4 E4B | 0 | 36/36 | 36/36 | 36/36 | 8.3 s |
| Qwen3.5 4B | 0 | 36/36 | 36/36 | 23/36 | 7.7 s |
| Gemma 4 E2B | 3 | 32/36 | 35/36 | 19/36 | 4.2 s |
| Qwen3.5 2B | 4 | 29/36 | 33/36 | 30/36 | 2.8 s |

Serve a model with:

```bash
llama-server -hf unsloth/gemma-4-E4B-it-GGUF:Q4_K_M --jinja -c 4096 -t 6 --port 8092
python llm_eval.py gemma4-e4b 8092
```

## Making Gemma 4 E4B faster (2026-09-27)

`bench.py` sends the reader's real prompt and schema with eight corpus
messages; `run_clean.sh` runs each llama.cpp configuration alone on the
machine. Measured on a Ryzen 5 5600G, six cores, no GPU; raw lines in
`speed_results.txt`.

| Configuration | Per message | Tokens/s | RAM |
|---|---|---|---|
| Q4_K_M, image encoder off, one slot | 9.5 s | 9.3 | 5.3 GB |
| QAT UD-Q4_K_XL | 8.3 s | 10.9 | 5.2 GB |
| QAT, `--lazy-mode on` | 8.2 s | 11.0 | 5.2 GB |
| QAT, n-gram drafting | 8.2 s | 11.0 | 5.2 GB |
| **QAT + MTP drafter, 4 ahead** | **3.7 s** | **27.6** | **5.4 GB** |
| QAT + MTP + n-gram | 4.0 s | 24.6 | 5.4 GB |
| QAT + MTP, 2 / 6 / 8 ahead | 5.1 / 4.1 / 4.1 s | 18.5 / 24.0 / 24.4 | 5.4 GB |

The drafter's answers were identical to the model's own on all eight
messages. The QAT build matched the original on seven and read one refusal
the original missed. Through `moat-intent` on the full corpus the QAT and
drafter setup had no fail-open, every payee right, 35 of 36 refusals, and a
median of 4.9 s. Of the 5.4 GB, about 3 GB is memory the process must hold;
the rest is the model file cached in RAM, which the operating system can
drop under pressure. `--lazy-mode` changed nothing on Windows; its measured
saving was on Linux. n-gram drafting never engaged with a JSON schema.

```bash
llama-server -m gemma-4-E4B-it-qat-UD-Q4_K_XL.gguf -md mtp-gemma-4-E4B-it.gguf \
  --spec-type draft-mtp --spec-draft-n-max 4 --no-mmproj -np 1 -c 2048 --jinja --port 8092
```

Both files are in `unsloth/gemma-4-E4B-it-qat-GGUF`.

## On a GPU (2026-09-27)

`colab_gpu_bench.ipynb`, generated by `make_colab_notebook.py` from the
reader's own prompt and corpus, runs the same measurement on a Colab Tesla
T4 and writes its results to Google Drive. Raw lines are at the end of
`speed_results.txt`.

| Setup on a T4 | Per message | Slowest 5% | Tokens/s | GPU memory |
|---|---|---|---|---|
| Gemma 4 E4B QAT alone | 1.51 s | 1.65 s | 56.7 | 2.7 GB |
| **With the MTP drafter** | **0.77 s** | **0.90 s** | **117.7** | **2.8 GB** |
| With the drafter, 4 at once | 1.96 s each | 2.44 s | 117 messages/minute | 3.0 GB |

Both single-request runs had no fail-open and scored 36 of 36 on payees,
refusals, amounts, currencies, references and cancels, judged on the raw
answer before grounding. The drafter was accepted 89% of the time, as on the
CPU. Any GPU with 4 GB of memory holds it.
